# x4js desktop application

An [x4js](https://x4js.org) application in a [Wails](https://wails.io) window: the interface is written in TypeScript, the system side in Go. The result is a single executable, which uses the web view of the system.

## Requirements

- [Go](https://go.dev/dl/), at least the version written in `go.mod`.
- The Wails command, version 2:

```
go install github.com/wailsapp/wails/v2/cmd/wails@latest
```

`wails doctor` checks that the dependencies of Wails are installed, and says what is missing. On Windows, Wails needs the WebView2 runtime.

## Develop

```
npm install
npm run dev
```

`npm run dev` builds the interface, then starts `wails dev`, which opens the application window.

- A change in the interface reloads the window.
- A change in a `.go` file rebuilds the application and restarts it.
- The executable of this mode is `build/bin/x4-wails-dev.exe`. Wails removes it when the command stops: an empty `build/bin` after `npm run dev` is normal.

At each start, `wails dev` also:

- runs `go mod tidy`, which downloads the Go modules and writes `go.sum`;
- writes in `go.mod` the version of Wails of the installed `wails` command, when they differ. To keep `go.mod` as it is, start it with `-nosyncgomod`.

## Build

```
npm run build
```

`npm run build` builds the interface, then runs `wails build`. The executable is written to `build/bin`, under the name given by `outputfilename` in `wails.json`. It contains the interface: it is the only file to distribute.

- The developer tools of the web view are not available in this executable. `wails build -s -devtools` enables them; `wails build -s -debug` makes a debug build, where they are enabled too.
- `wails build` does not change the version of Wails in `go.mod`: it warns when it differs from the installed command. `-u` updates it.

## How it is organized

| File or folder | Content |
|---|---|
| `src` | The x4js interface. It has no access to the system. |
| `app.go` | The Go side: what the interface can ask. |
| `main.go` | Creates the window and gives it the interface. |
| `wails.json` | The Wails project: name, version, commands. |
| `public` | `index.html`, copied to the output. |
| `bin` | The interface built by x4js. `main.go` compiles it into the executable. |
| `build` | Icons and manifests used by Wails, and the executable in `build/bin`. |
| `wailsjs` | Modules generated by Wails (see below). Not used, left out of Git. |

The two scripts build the interface themselves with x4js, then call `wails` with `-s`, which tells it to skip its own build of the interface. Running `wails dev` or `wails build` without `-s` works too: Wails then runs the `frontend:` commands of `wails.json`.

## Calling Go from the interface

The interface cannot read a file or open a system dialog by itself. It asks the Go side through `host`:

```ts
import { host } from "./host";

const file = await host.openTextFile();
```

To add a function, edit two files:

1. `app.go`: write an exported method on `App`. It can return nothing, a value, an error, or a value and an error.
2. `src/host.ts`: declare it in `GoApp` with the same name, add it to `Host`, and forward it in `host`.

A call returns a promise. An error returned by Go rejects it with the text of the error. With Wails 2.16 the rejection is an `Error` whose `message` is that text; older versions, 2.10 for one, reject with the text itself, a string.

Values that cross the boundary are converted to JSON: the `json` names of a Go struct are the field names seen by the interface.

At each `wails dev` and `wails build`, Wails also generates JavaScript modules for the bound Go types, in the `wailsjs` folder. The template does not use them: `src/host.ts` plays that role with two declarations.

The comments of `app.go` describe these rules in more detail.

## Name and version

`x4js create` sets the name in `package.json` only. For the window title, the executable and the version, edit `wails.json`: `name`, `outputfilename` and `info`. The module name is the first line of `go.mod`.
